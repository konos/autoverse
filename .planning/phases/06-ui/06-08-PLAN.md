<objective>
06-VERIFICATION.md gap 1(CR-01)을 닫는다: 고지 확인 흐름이 `settings:set-login-mode` 쓰기 실패를
감지하지 못하고 모달을 "확인 완료"로 닫는 계약 불일치를 구조적으로 제거한다.

Purpose: ROADMAP Phase 06 SC2 정정본의 "확인해야만 진행"은 지금 **정상 경로에서만** 성립한다.
디스크 쓰기가 실패하면 `apiModeNoticeAckedVersion` 은 이미 영속됐는데 `loginMode` 는 바뀌지
않은 어긋난 상태가 남고, 고지 모달은 두 번 다시 뜨지 않는다(D-10 의 재노출 판정이 확인된
버전을 보기 때문). 이 phase 가 반복해서 표방한 "UI 가 거짓말하지 않는다" 에 정면으로 위배되는
지점이며, 렌더러 컴포넌트 테스트가 전무해 315개 테스트 스위트가 이것을 잡지 못했다.

Output: 두 경로의 실패 계약을 소유하는 순수 모듈 `src/renderer/login-mode-actions.ts`, 그
계약을 잠그는 회귀 테스트, 그리고 모달 경로가 실패를 삼키는 함수를 **주입받을 수 없게** 만든
`LoginPanel` props 재설계.
</objective>

**출처:** `06-VERIFICATION.md` frontmatter `gaps[0]` (status: partial) — 06-REVIEW.md CR-01 과
동일 결함을 검증자가 코드를 직접 읽어 독립적으로 재확인한 것.

**결함의 정확한 형태 (검증자 서술 그대로):**
`LoginPanel.tsx:95-107` `handleAcknowledge()` 는 `onSetLoginMode()` 가 실패 시 예외를 던질 것을
전제로 try/catch 를 구성했다. 그러나 실제로 주입되는 `App.tsx:130-139` `handleSetLoginMode()` 는
자신의 실패를 catch 해 `loginError` 배너에만 표시하고 **절대 다시 던지지 않는다** — 이는 원래
설계 대상이었던 탭 클릭(fire-and-forget) 경로에서는 올바른 동작이다(App.tsx 122-129행 주석과
UI-SPEC E1 error 가 그렇게 요구한다). 문제는 정반대 계약을 요구하는 모달 경로가 같은 함수를
재사용한다는 점이다.

**소비자에게 보이는 결과:** 디스크 쓰기 오류로 `settings:set-login-mode` 가 실제로 실패해도
`await onSetLoginMode("api")` 가 정상 resolve → `setNoticeOpen(false)` 실행 → 모달이 "확인 완료"
로 닫힌다. `loginMode` 는 안 바뀌었지만 `apiModeNoticeAckedVersion` 은 이미 영속되어 다음에 API
탭을 다시 눌러도 고지가 재노출되지 않는다. **정상 경로(쓰기 성공)는 온전하다.**

**검증자가 제안한 처치:** 모달 전용 strict 변형(예: `setLoginModeOrThrow`)을 추가해
`handleAcknowledge` 에서만 쓰고, fire-and-forget `handleSetLoginMode` 는 탭 경로에 그대로 둔다.

**이 플랜이 채택한 처치와 그 차이 — 왜 다르게 가는가:**
검증자 제안은 올바르지만 **결함이 재발할 수 있는 형태**를 남긴다. strict/safe 두 setter 를 둘 다
prop 으로 내려보내면 "모달 경로에 어느 것이 연결되었는가" 라는 배선 결정이 다시 `App.tsx` 의
JSX 한 줄에 흩어지고, 그 한 줄은 여전히 어떤 테스트로도 잠기지 않는다 — CR-01 을 만든 것이
정확히 그 형태다.

대신 이 플랜은 **모달 경로가 로그인 방식 저장 함수를 아예 prop 으로 받지 않도록** 한다.
`onAckNotice` prop 을 제거하고 `onAcknowledgeNotice(version): Promise<AcknowledgeOutcome>` 하나로
대체한다. 확인 흐름 전체(확인 상태 저장 → 모드 저장 → 성패 판정)가 `createLoginModeActions()`
안에 들어가고, 그 팩토리가 내부적으로 어느 계약을 쓰는지 결정한다. 결과적으로 "실패를 삼키는
함수를 모달 경로에 꽂는다"는 실수를 **타입 수준에서 표현할 수 없게** 된다. 검증자 제안이 요구한
성질(모달은 실패를 감지하고, 탭은 그대로 삼킨다)은 그대로 만족한다.

**회귀 커버리지:** 검증자가 함께 지적한 "App.tsx/LoginPanel.tsx 에 렌더러 컴포넌트 테스트가
전혀 없다"는 사실이 이 결함이 보이지 않았던 이유다. 이 저장소는 vitest `environment: "node"` 에
jsdom/@testing-library 가 없고 `06-VALIDATION.md` § Test Infrastructure 가 이를 **제약으로 명시**
하며(신규 의존성 금지), 기존 관례는 "판단 로직을 순수 함수로 추출해 그 함수를 테스트한다" 다.
따라서 컴포넌트를 렌더링하는 테스트가 아니라 **컴포넌트가 호출하는 액션 모듈을 추출해** 회귀를
잠근다. 이는 06-06 이 `login-panel-view.ts` 로 이미 세운 이 phase 자신의 패턴이다.
