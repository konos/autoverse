# Phase 06 — UI Design Contract

> Visual and interaction contract for **로그인 방식 선택 UI + 실패 안내**.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Primary sources: `06-CONTEXT.md` (D-01~D-15, locked), `06-RESEARCH.md` (§Architecture Patterns,
> §Standard Stack), `src/renderer/components/LoginPanel.tsx`, `src/renderer/styles.css`.

## Design System

| Property | Value |
|----------|-------|
| Tool | **none** — this project uses plain CSS (`src/renderer/styles.css`) + inline `style={{}}` props. There is no Tailwind, no shadcn, no CSS-in-JS, and no existing modal/dialog component anywhere in the codebase (`grep -riE "dialog\|modal\|overlay"` over styles.css → 0 matches). This is an established convention, not a gap — `components.json` intentionally absent. Do NOT initialize shadcn for this phase; it would contradict the existing idiom and add a dependency mismatch (Electron 33 CommonJS main / no bundler config for it). |
| Preset | not applicable |
| Component library | none — native `<dialog>` element (`.showModal()`) used for the new notice modal (D-09), per `06-RESEARCH.md` Pattern 3 (built-in focus trap, Esc, backdrop, top-layer) |
| Icon library | none — codebase uses text-only labels and CSS `--color-*` tokens for state signaling, no icon package installed or imported anywhere. Where a visual marker is needed (e.g. locked/warning), use a plain Unicode glyph (`⚠`), never an icon-font/SVG-sprite dependency |
| Font | `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif` (existing system font stack, `body` selector, unchanged) |

**Registry safety gate: not applicable** — no shadcn, no registries of any kind used in this phase.

## Spacing Scale

This phase does not renovate existing spacing (out of scope — `LoginPanel.tsx`'s current
rem-based values are legacy and untouched except where a class is reused verbatim). The scale
below governs only the **new** elements this phase introduces: the mode-locked badge, the notice
modal, and the persistent inline notice banner.

Declared values (multiples of 4, root font-size 16px so `1rem = 16px`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (0.25rem) | Badge internal padding, gap between icon glyph and text |
| sm | 8px (0.5rem) | Gap between tabs, gap between modal paragraphs |
| md | 16px (1rem) | Modal content padding, notice banner padding |
| lg | 24px (1.5rem) | Modal top/bottom padding around button row |
| — | 32px+ | Not used this phase (no layout at this scale is introduced) |

**Exceptions:**
- Reused existing classes (`.card`, `.btn`, `.form-input`, `.form-field`, `.button-row`,
  `.error-message`, `.status-row`) keep their current pre-existing padding/margin values exactly
  as defined in `styles.css` (e.g. `.card { padding: 1.25rem }` = 20px, not a multiple of 4).
  Normalizing these is out of scope for this phase — do not touch values on classes this phase
  does not functionally change.
- `.login-mode-tabs` (existing inline-styled wrapper, `gap: 0.5rem` = 8px) — already compliant,
  keep as-is.

## Typography

New elements introduced by this phase (badge, modal, notice banner, failure message content)
must use ONLY the following 3 sizes / 2 weights. Existing reused classes (`.btn`, `.form-label`,
`.card-title`, `.app-title`) keep their current values unchanged (see Exceptions).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (0.875rem) | 400 (regular) | 1.5 |
| Label / small | 12.8px (0.8rem) | 400 (regular), color `var(--color-muted)` | 1.4 |
| Heading (modal title) | 16px (1rem) | 600 (semibold) | 1.2 |
| Display | not used this phase | — | — |

**Weights (exactly 2, for new elements only):** 400 regular (body copy, notice text, failure
messages), 600 semibold (modal title only — `<h2>` inside `<dialog>`).

**Exceptions:** `.btn`/`.form-label` (existing weight 500) and `.app-title` (existing weight 600
at 1.4rem/22.4px) are pre-existing, unchanged, out of scope. Do not introduce a third new weight
anywhere in this phase's new markup.

## Copywriting Contract

All strings are final. Do not rephrase, shorten, or "improve" at implementation time — every word
here was chosen to avoid restating a disproven claim (see `06-CONTEXT.md` "UI가 거짓말하지 않게
한다").

### Core CTAs / states

| Element | Copy |
|---------|------|
| Primary CTA (this phase's blocking gate) | "확인했습니다" — notice-modal acknowledge button |
| Secondary CTA (existing, unchanged) | "로그인" — credential form submit button |
| Empty state | Not applicable this phase — no new list/collection UI is introduced. Existing credential-form empty-field state (`disabled` submit until both fields filled) is pre-existing and unchanged. |
| Error state | See "Failure reason → copy" table below — this table IS the phase's error-state contract (R020) |
| Destructive confirmation | Not applicable this phase — the existing "로그아웃 + 자격 증명 삭제" button has no confirmation dialog today and this phase does not add one (deferred; see `06-CONTEXT.md` Deferred Ideas "로그아웃 UI 갭"). Do not add a confirmation modal here — it would create two modal patterns in one phase where only D-09's notice modal is in scope. |

### Login mode selector labels (D-01/D-04)

| Element | Copy |
|---------|------|
| API mode tab | `API 로그인` |
| Browser mode tab | `브라우저 로그인` (unchanged from current code) |

Rationale: "API 로그인" matches the term R016/ROADMAP already use ("API 통신") and stays honest —
it does not claim "no browser at all" (D-01: a hidden `BrowserWindow` is still involved) and does
not repeat the disproven "이메일 로그인"-as-OTP-flow framing. Do not use "이메일 로그인" as the
final label — that name implied the disproven multi-step OTP contract.

### Locked-by-env indicator (D-06)

| Element | Copy |
|---------|------|
| Badge label (always exactly this string, per D-06 wording) | `환경변수로 고정됨` |
| Badge detail text (tooltip / small text under badge — must state the ACTUAL resolved mode, never the raw env value) | `AUTOVERSE_LOGIN_MODE 환경변수가 설정되어 있어 이 화면에서 방식을 변경할 수 없습니다. 현재 적용 중: {현재 모드 라벨}` where `{현재 모드 라벨}` is literally "API 로그인" or "브라우저 로그인" (never the raw env string) |

Both tabs render `disabled` (existing `.btn:disabled` style, `opacity: 0.5`, `cursor: not-allowed`)
when `lockedByEnv === true`. The badge sits inline next to the tab row, not inside a tab.

### Notice modal (D-08/D-09/D-10) — `ApiModeNoticeModal`

| Element | Copy |
|---------|------|
| Title (`<h2>`, `aria-labelledby` target) | `API 로그인 방식 안내` |
| Point 1 | `Weverse 보안 확인(캡차)이 뜨면 이 방식으로 로그인이 실패할 수 있습니다. 이 경우 브라우저 로그인 방식을 사용해주세요.` |
| Point 2 | `자동 재로그인 기능이 없습니다. 앱을 다시 시작하거나 로그인 토큰이 만료되면 직접 다시 로그인해야 합니다.` |
| Confirm button | `확인했습니다` |
| Cancel path (Escape key or an explicit cancel affordance) | `취소` — clicking Cancel or pressing Escape closes the dialog WITHOUT acknowledging (does not write `apiModeNoticeAckedVersion`) and reverts the mode selection to whatever it was before the API tab was clicked (does not switch to `"api"`). This must be true even though `<dialog>` closes on Escape by default — the close handler, not just the visual close, is what must NOT count as acknowledgement. |

**Exactly these two points, in this order, nothing else added.** Do not include headless-mode
implementation detail, rung2 status, or any other internal detail (explicit CONTEXT constraint).

### Persistent inline notice (D-08/D-09, shown whenever active mode is `"api"`, post-acknowledgement)

| Element | Copy |
|---------|------|
| Banner text | `API 로그인은 Weverse 보안 확인(캡차) 시 실패할 수 있으며, 자동 재로그인을 지원하지 않습니다.` |

Single sentence, no title, no dismiss button (it is not a one-time toast — it must remain visible
for as long as API mode is active, per D-09 "이후 상시 인라인"). Renders in the same box style as
`.consent-body` (background `var(--color-bg)`, border `var(--color-border)`, radius 6px, padding
0.5rem 0.75rem) plus the `var(--color-warning)` 3px left-border accent described in the Color
section.

### Failure reason → copy (D-12/D-13/D-14, this is the R020 contract)

| Failure signal (`LoginFailureReason`) | Copy shown to user | Extra affordance |
|---|---|---|
| `captcha` (D-13 — corrected from the disproven "otp" misclassification) | `Weverse가 보안 확인을 요구해 앱 안 로그인으로는 진행할 수 없습니다. 브라우저 로그인을 사용해주세요.` | Button: `브라우저 로그인으로 전환` (immediately switches the active tab to browser mode) |
| `form-error` (Weverse's own DOM-rendered error text) | Passthrough of the DOM text, after preprocessing: (1) `.trim()`, (2) truncate to 120 characters with a trailing `…` if longer (full text still goes to the log panel, untruncated), (3) still pass through `maskSensitive()` before rendering — defense-in-depth even though Weverse copy is not expected to contain secrets | none |
| `timeout` (25s DOM-polling timeout) | `로그인 응답 대기 시간을 초과했습니다. 다시 시도하거나 브라우저 로그인을 사용해주세요.` | none required, but a "브라우저 로그인으로 전환" button MAY reuse the same affordance as `captcha` if convenient — not required by CONTEXT |
| `network-error` (thrown exception, non-HTTP) | `네트워크 오류로 로그인에 실패했습니다. 인터넷 연결을 확인한 뒤 다시 시도해주세요.` | Masked identifier appended in parentheses, small/muted text — see identifier format below |
| `token-ladder-failed` (`ApiAuthError` from `acquireFaneventToken()`) | `로그인은 성공했지만 서비스 이용에 필요한 토큰을 확보하지 못했습니다. 다시 로그인해주세요.` | Masked identifier appended (same format) |
| `unknown` / unmapped (D-14 catch-all — also the landing zone for the legacy `'otp'` DOM branch per `06-RESEARCH.md` Open Question 1 recommendation (a)) | `로그인에 실패했습니다. 로그 패널에서 자세한 내용을 확인하세요.` | Masked identifier appended (same format) |

**Identifier format (all three rows that carry one):** small, visually de-emphasized text appended
after the main sentence, in parentheses: `(식별자: {maskedIdentifier})`. Suggested style: reuse
`.token-preview` class (monospace, `var(--color-muted)`, small background chip) so it visually
reads as "technical detail, not the main message." **The identifier MUST be the return value of
`maskSensitive(rawIdentifier)`, never the raw exception message or raw code** — this is the R010
gate; `CredentialLoginResult.message` does not pass through `logService`'s automatic masking, so
the call site must apply `maskSensitive()` explicitly (see `06-RESEARCH.md` Pitfall 2).

All six rows render in the existing `.error-message` slot (`role="alert"`), per D-15 — no new
message region.

## Interaction Contract

Additional prescriptive detail beyond copy, needed because this phase changes structure, not just
labels.

1. **Selector visibility spans both login states (structural change required).** In the current
   code, the mode tabs render only inside `{!status.isLoggedIn && (...)}`. D-07 ("로그인된 상태에서
   방식을 바꾸면 설정만 바뀌고 현재 세션은 유지된다") is only meaningful if the selector is visible
   and operable while logged in too. **This phase must move the tab row out of the
   `!status.isLoggedIn` gate** so it renders unconditionally near the top of the `LoginPanel` card
   (directly under the status row, above the credential form / logged-in button row). When
   `status.isLoggedIn === true`, the tabs still render and remain clickable; only the
   email/password form and the "로그인" button stay hidden (existing behavior for that part is
   unchanged).
2. **Tab click while already-acknowledged does not re-show the modal.** The modal (D-09) is
   test-worthy as a pure decision function: `shouldShowApiModeNotice(ackedVersion: number | null,
   currentVersion: number): boolean` → `ackedVersion === null || ackedVersion < currentVersion`.
   Clicking the API tab always calls this function first; only a `true` result opens the modal.
   This keeps the interaction contract expressible as a pure function per the codebase's
   render-nothing test convention (`profile-form-validation.test.ts`).
3. **Cancel/Escape reverts tab selection, does not persist "api".** If the modal is dismissed via
   Cancel or Escape, the underlying login-mode selection must not change — the previously active
   tab (browser, or whatever was active) stays visually selected and `settings:set-login-mode`
   must not be called with `"api"`. Only clicking "확인했습니다" both (a) calls
   `settings:ack-notice(currentVersion)` and (b) calls `settings:set-login-mode("api")`. These two
   effects are coupled — do not persist the mode switch before/without the acknowledgement.
4. **Version bump re-shows the modal exactly once per bump.** Per D-10, if `NOTICE_VERSION` (a
   plain integer, starting at `1`) is incremented in a future change, `ackedVersion < currentVersion`
   becomes true again and the modal reappears the next time API mode is (re)selected — even for a
   user who already acknowledged an older version. The persistent inline notice text also always
   reflects the CURRENT version's copy, never a stale acknowledged version's copy.
5. **Locked-by-env forecloses both the modal and manual tab switching.** When `lockedByEnv ===
   true`, clicking either (disabled) tab does nothing — no modal, no IPC call. The badge is the
   only feedback.
6. **Failure message region is reused, not duplicated.** The notice modal (D-09) and the failure
   message (D-15) must never both be visible at the same time — the modal only ever appears
   immediately after a tab click (before any login attempt), the failure message only ever appears
   after a login attempt. There is no code path where both are simultaneously mounted; do not add
   defensive logic that tries to "close the other one" — their trigger conditions are already
   disjoint by construction.
7. **Accessibility floor:** `<dialog>` gets `aria-labelledby="api-mode-notice-title"` pointing at
   the `<h2>` (per `06-RESEARCH.md` Pattern 3). The failure-message paragraph keeps
   `role="alert"` (existing). Focus moves into the dialog on `showModal()` (native browser
   behavior — verify a focusable element, e.g. "확인했습니다", receives focus). Escape must fire
   `onClose`-equivalent logic that goes through the same "does not acknowledge" path as clicking
   Cancel — verify this explicitly since it is not automatic just because Escape closes the
   `<dialog>` visually.
