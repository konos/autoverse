## Spacing Scale

This phase does not renovate existing spacing (out of scope — `LoginPanel.tsx`'s current
rem-based values are legacy and untouched except where a class is reused verbatim). The scale
below governs only the **new** elements this phase introduces: the mode-locked badge, the notice
modal, and the persistent inline notice banner.

Declared values (multiples of 4, root font-size 16px so `1rem = 16px`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (0.25rem) | Badge internal padding, gap between icon glyph and text |
| sm | 8px (0.5rem) | Gap between tabs, gap between modal paragraphs |
| md | 16px (1rem) | Modal content padding, notice banner padding |
| lg | 24px (1.5rem) | Modal top/bottom padding around button row |
| — | 32px+ | Not used this phase (no layout at this scale is introduced) |

**Exceptions:**
- Reused existing classes (`.card`, `.btn`, `.form-input`, `.form-field`, `.button-row`,
  `.error-message`, `.status-row`) keep their current pre-existing padding/margin values exactly
  as defined in `styles.css` (e.g. `.card { padding: 1.25rem }` = 20px, not a multiple of 4).
  Normalizing these is out of scope for this phase — do not touch values on classes this phase
  does not functionally change.
- `.login-mode-tabs` (existing inline-styled wrapper, `gap: 0.5rem` = 8px) — already compliant,
  keep as-is.

### Visual priority within the LoginPanel card

Resolves the checker's Dimension 2 recommendation — implementers must not guess the reading order.
Top-to-bottom, the card's attention order is:

1. **Status row** (existing, unchanged) — "로그인 완료 / 미로그인" is the first thing scanned; it answers
   "am I usable right now?"
2. **Mode selector tabs** — the active tab is the only accent-blue element in the resting state, so it
   is the strongest visual pull below the status row. This is intentional: the phase exists to make the
   chosen method obvious.
3. **Persistent inline notice banner** (API mode only) — sits directly under the tabs. Its warning
   left-border accent gives it weight *without* accent blue, so it reads as a standing condition
   attached to the tab above it, not as a call to action.
4. **Credential form / logged-in button row** — the working area.
5. **Failure message** — when present it appears in the existing `.error-message` slot and, being the
   only destructive-colored text on screen, temporarily outranks everything except the status row.

The env-locked badge deliberately does **not** compete: it is muted/neutral and reads as an annotation
on the tab row rather than a separate focal point.

## Interaction Contract

Additional prescriptive detail beyond copy, needed because this phase changes structure, not just
labels.

1. **Selector visibility spans both login states (structural change required).** In the current
   code, the mode tabs render only inside `{!status.isLoggedIn && (...)}`. D-07 ("로그인된 상태에서
   방식을 바꾸면 설정만 바뀌고 현재 세션은 유지된다") is only meaningful if the selector is visible
   and operable while logged in too. **This phase must move the tab row out of the
   `!status.isLoggedIn` gate** so it renders unconditionally near the top of the `LoginPanel` card
   (directly under the status row, above the credential form / logged-in button row). When
   `status.isLoggedIn === true`, the tabs still render and remain clickable; only the
   email/password form and the "로그인" button stay hidden (existing behavior for that part is
   unchanged).
2. **Tab click while already-acknowledged does not re-show the modal.** The modal (D-09) is
   test-worthy as a pure decision function: `shouldShowApiModeNotice(ackedVersion: number | null,
   currentVersion: number): boolean` → `ackedVersion === null || ackedVersion < currentVersion`.
   Clicking the API tab always calls this function first; only a `true` result opens the modal.
   This keeps the interaction contract expressible as a pure function per the codebase's
   render-nothing test convention (`profile-form-validation.test.ts`).
3. **Cancel/Escape reverts tab selection, does not persist "api".** If the modal is dismissed via
   Cancel or Escape, the underlying login-mode selection must not change — the previously active
   tab (browser, or whatever was active) stays visually selected and `settings:set-login-mode`
   must not be called with `"api"`. Only clicking "확인했습니다" both (a) calls
   `settings:ack-notice(currentVersion)` and (b) calls `settings:set-login-mode("api")`. These two
   effects are coupled — do not persist the mode switch before/without the acknowledgement.
4. **Version bump re-shows the modal exactly once per bump.** Per D-10, if `NOTICE_VERSION` (a
   plain integer, starting at `1`) is incremented in a future change, `ackedVersion < currentVersion`
   becomes true again and the modal reappears the next time API mode is (re)selected — even for a
   user who already acknowledged an older version. The persistent inline notice text also always
   reflects the CURRENT version's copy, never a stale acknowledged version's copy.
5. **Locked-by-env forecloses both the modal and manual tab switching.** When `lockedByEnv ===
   true`, clicking either (disabled) tab does nothing — no modal, no IPC call. The badge is the
   only feedback.
6. **Failure message region is reused, not duplicated.** The notice modal (D-09) and the failure
   message (D-15) must never both be visible at the same time — the modal only ever appears
   immediately after a tab click (before any login attempt), the failure message only ever appears
   after a login attempt. There is no code path where both are simultaneously mounted; do not add
   defensive logic that tries to "close the other one" — their trigger conditions are already
   disjoint by construction.
7. **Accessibility floor:** `<dialog>` gets `aria-labelledby="api-mode-notice-title"` pointing at
   the `<h2>` (per `06-RESEARCH.md` Pattern 3). The failure-message paragraph keeps
   `role="alert"` (existing). Focus moves into the dialog on `showModal()` (native browser
   behavior — verify a focusable element, e.g. "확인했습니다", receives focus). Escape must fire
   `onClose`-equivalent logic that goes through the same "does not acknowledge" path as clicking
   Cancel — verify this explicitly since it is not automatic just because Escape closes the
   `<dialog>` visually.
