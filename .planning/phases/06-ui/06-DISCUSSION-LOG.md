## API 모드의 실체 정의

### Q1. 사용자가 고를 "API 통신 모드"는 실제로 어느 경로에 배선돼야 하는가?

| Option | Description | Selected |
|--------|-------------|----------|
| 헤드리스 자동입력 (추천) | API 모드 = `credentialLogin()`. 앱 안에서 이메일/비번을 받아 보이지 않는 창이 대신 로그인. Phase 05가 실계정으로 검증한 유일 동작 경로. `credentialLoginApi`는 사실상 폐기 | ✓ |
| 순수 HTTP 유지 + 실패 안내 | `credentialLoginApi()` 그대로 두고 캡차 실패 시 사유를 안내. 계약이 바뀌면 동작할 여지를 남기지만 항상 실패하는 옵션을 제공하는 셈 | |
| 재라벨링 (API란 말 제거) | 사용자 체감 기준 라벨링("앱 백그라운드 로그인" vs "브라우저 로그인"). 배선은 1번과 같으나 로드맵/요구사항 용어를 전부 변경해야 함 | |

**User's choice:** 헤드리스 자동입력
**Notes:** 05-CONTEXT의 D-04(로그인 방식 최종 결정 보류)가 이 답으로 해소됨. 코드 확인 결과 `credentialLoginApi`는 단순 실패가 아니라 실제 흐름에 없는 `requestOtpSession()`을 호출하고 `-25044`를 "OTP 필요"로 오독해 **오지 않을 메일을 기다리게 하는 거짓 OTP 화면**을 띄운다는 점이 선택의 결정적 근거가 됨.

### Q2. 반증된 계약 기반 코드를 이번 phase에서 어떻게 처리하는가?

| Option | Description | Selected |
|--------|-------------|----------|
| 지금 제거 (추천) | 05-CONTEXT D-07이 말한 "정의 확정 후 일괄 정리" 시점. 남겨두면 모드 게이트 분기가 살아있어 재배선 위험 + 거짓 OTP 화면이 이 phase 목표와 충돌. rung2 관련 `exchangeForService()`는 유지 | ✓ |
| 배선만 끊고 코드는 보존 | IPC 분기와 OTP UI만 제거, 메서드는 deprecated 주석과 함께 존치. 캡차 실패 폴백으로 OTP가 실재할 가능성(R018 미입증) 대비 | |
| 이번 phase 에선 손대지 않음 | 선택/고지/안내 계층만 다루고 정리는 Phase 07 이후로. 그때까지 거짓 OTP 화면 노출 경로가 남음 | |

**User's choice:** 지금 제거

### Q3. API 모드에서 저장된 자격증명으로의 자동 로그인/재로그인을 어떻게 하는가?

| Option | Description | Selected |
|--------|-------------|----------|
| 모드 관계없이 차단 유지 (추천) | 게이트를 모드 조건이 아니라 "무인 로그인 요청 발생 여부"로 재정의. 캡차가 언제든 인터랙티브 챌린지를 띄울 수 있어(05에서 1차 시도 timeout) 무인 재로그인은 어느 모드에서도 보장 불가. 다른 계정 오동작 방지라는 실증된 가치도 유지 | ✓ |
| API 모드에서도 허용 | 게이트를 걷어내고 두 모드 모두 무인 헤드리스 자동 로그인 시도. 사용성은 좋아지나 05-01의 피해(다른 계정 알림 메일) 재발 위험 + R021/R022의 "자동 재로그인 불가" 전제가 무너져 Phase 07 설계까지 바뀜 | |
| 게이트 손대지 않음 | 현재 코드 유지. API 모드 사용자는 항상 수동 로그인해야 하고, 반증된 사유 문구("매 로그인마다 OTP 필요")가 그대로 남음 | |

**User's choice:** 모드 관계없이 차단 유지
**Notes:** 답변이 "브라우저 모드의 자동 로그인까지 끄는가"로 읽힐 수 있어 Q4로 범위를 명확화함.

### Q4. 차단 범위 확정 — 세션 복원(쿠키)과 무인 로그인 시도 중 무엇을 막는가?

| Option | Description | Selected |
|--------|-------------|----------|
| (2)만 차단, (1)은 허용 | 두 모드 모두 살아있는 쿠키 토큰으로의 세션 복원은 허용, 저장 자격증명으로의 무인 headless 로그인은 시도하지 않음. 외부 로그인 요청은 항상 사용자 클릭에서만 발생 — 05-01 피해의 근본 원인을 막으면서 재시작 후 바로 쓰는 경험은 유지 | ✓ |
| (1)도 (2)도 전부 차단 | 앱 시작 시 어떤 자동 인증도 없이 항상 사용자가 로그인 버튼을 누름. 가장 보수적이나 기존 브라우저 모드 동작이 더 크게 바뀜 | |
| 브라우저는 현상태, API만 차단 | 현재 코드와 동일한 효과. 게이트 주석만 반증된 사유(OTP)에서 실제 사유(reCAPTCHA·계정 오동작 방지)로 정정 | |

**User's choice:** (2)만 차단, (1)은 허용
**Notes:** 이 결정은 브라우저 모드의 `tryAutoLogin()` 자격증명 경로도 제거하므로 ROADMAP Phase 06 SC1("기존 브라우저 로그인 동작 변경 없이")과 **의도적 편차**가 발생함을 사용자에게 고지하고 진행. CONTEXT.md D-03에 예외로 명시. 부수 효과로 R022(토큰 만료 사전 경고, Phase 07)의 필요성이 두 모드 전체로 확대됨.

## 선택기 UI + 선택값 영속

### Q1. 로그인 방식 선택기를 어떤 형태로 두는가?

| Option | Description | Selected |
|--------|-------------|----------|
| 기존 탭을 영속 선택기로 승격 (추천) | LoginPanel의 현재 탭을 그대로 쓰되 라벨 재작성, 클릭 즉시 영속 저장, 기본값을 브라우저로 변경. 새 UI 없이 기존 구조 재사용 | ✓ |
| 별도 "로그인 방식" 세그먼트 | 상단에 명시적 라벨 + 라디오/세그먼트를 두고 그 아래 해당 모드 폼. 기존 탭 제거. "설정을 고르는 것"임이 시각적으로 더 분명 | |
| 앱 설정 영역으로 분리 | 별도 설정 카드/모달에서 방식 선택, LoginPanel은 현재 모드만 표시. 새 UI 영역과 화면 전환이 추가됨 | |

**User's choice:** 기존 탭을 영속 선택기로 승격

### Q2. 선택값을 어디에 저장하는가?

| Option | Description | Selected |
|--------|-------------|----------|
| 별도 평문 settings.json (추천) | userData에 신설. 비민감 값이라 암호화 불필요하고 safeStorage 미지원 환경에서도 모드 선택이 깨지지 않음. 손상/미존재 시 기본값(브라우저) 폴백. Phase 07 설정도 여기 축적 가능 | ✓ |
| profile.enc 확장 | 기존 safeStorage 패턴 재사용으로 새 파일/패턴을 늘리지 않음. 단 미지원 시 예외가 나고 프로필 삭제 시 로그인 방식도 함께 사라지는 결합 발생 | |
| 압축 안 함 — planner 재량 | 저장 위치/형식을 구현 세부로 보고 planner에게 위임. "재시작 후 유지"(SC1)와 "기본값 브라우저"만 계약으로 고정 | |

**User's choice:** 별도 평문 settings.json
**Notes:** `ProfileStore`가 `safeStorage.isEncryptionAvailable()` false 시 **예외를 던진다**는 코드 확인이 근거. preload에 `settings:*` 네임스페이스가 없어 신설 필요.

### Q3. `AUTOVERSE_LOGIN_MODE` env와 저장된 설정의 우선순위는?

| Option | Description | Selected |
|--------|-------------|----------|
| env 우선 (설정 무시) | env가 설정돼 있으면 저장값을 덮어씀. 개발/QA에서 앱 상태를 건드리지 않고 모드 강제 가능하고 기존 `resolveLoginMode()` 테스트와 호환. 단 UI 표시값과 실제 동작이 엇갈릴 수 있어 "환경변수로 고정됨" 표시 필요 | ✓ |
| 저장값 우선 (env는 초기값만) | 사용자가 한 번이라도 선택했으면 그 값이 항상 이김. UI가 항상 진실을 말하지만 개발 중 강제 전환 불가 | |
| env 제거 | `AUTOVERSE_LOGIN_MODE`를 없애고 설정만 남김. 가장 단순하고 진실의 근원이 하나가 되나 기존 `login-mode.test.ts`와 개발 편의성을 잃음 | |

**User's choice:** env 우선 (설정 무시)
**Notes:** "UI가 거짓말하지 않도록 선택기에 '환경변수로 고정됨' 표시 + 조작 불가"를 파생 필수 요구사항으로 확정하고 사용자에게 고지함.

### Q4. 로그인된 상태에서 방식을 바꾸면?

| Option | Description | Selected |
|--------|-------------|----------|
| 설정만 바뀌고 세션은 유지 | 현재 토큰/로그인 상태 보존, 바뀐 방식은 다음 로그인부터 적용. 신청 대기 중 실수로 탭을 눌러도 세션이 날아가지 않아 안전 | ✓ |
| 로그인된 동안 선택기 비활성화 | 방식 변경은 로그아웃 상태에서만. 상태가 섞일 여지가 없고 신청 직전 사고를 원천 방지하나 바꾸려면 로그아웃해야 함 | |
| 전환 시 로그아웃 확인 후 진행 | "방식을 바꾸면 현재 세션이 종료됩니다" 확인 후 로그아웃. 모드와 세션이 항상 일치하지만 다이얼로그가 늘고 대기 중 오조작 위험 잔존 | |

**User's choice:** 설정만 바뀌고 세션은 유지

## 제약 고지 문구·시점

### Q1. 고지 문구에 무엇까지 담는가?

| Option | Description | Selected |
|--------|-------------|----------|
| 사용자 체감 중심 2가지 (추천) | (1) Weverse 보안 확인이 뜨면 로그인 실패 가능, 그때는 브라우저 방식 사용 (2) 자동 재로그인 없음, 재시작/만료 시 직접 로그인. 헤드리스·rung2 등 내부 구현은 언급하지 않음 | ✓ |

**Notes:** R021/SC2 원문의 "매 로그인마다 이메일 OTP 필요"는 HAR 실측으로 반증됨(호출 0건). 그대로 쓰면 사용자에게 거짓을 안내하게 되므로 사용 금지로 확정.

## 실패 사유 한국어 안내

### Q1. 한국어 안내 매핑의 대상 범위는?

| Option | Description | Selected |
|--------|-------------|----------|
