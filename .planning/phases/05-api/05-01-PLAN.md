<objective>
Phase 05 의 존재 이유인 R019 리스크를 가장 먼저 해소한다. 이메일/비밀번호 → 이메일 OTP → 팬이벤트 토큰까지 **한 경로만** 종단 배선한 트레이서를 만들고, 실계정으로 그 경로가 실제로 통하는지를 사람이 직접 검증한다.

핵심 미지수는 하나다: `by-credentials-with-otp` 가 돌려주는 account 토큰(또는 `by-access-token` 으로 교환한 토큰)이 `fanevent-v2.weverse.io` 에서 Bearer 로 통하는가. 실서버 프로브로 교환 엔드포인트가 실존하고 Authorization 헤더를 요구한다는 것까지는 확인됐지만(RESEARCH.md 발견 3), 200 성공 응답과 그 토큰의 팬이벤트 호환성은 실계정 없이 확인 불가다.

그래서 사다리(ladder)를 **런타임 코드**로 구현한다. 1번(교환 없이 직접) → 2번(by-access-token 교환 후) 순으로 시도하고 성공한 쪽을 채택한다. 스파이크는 "어느 사다리가 이겼는지"를 관측할 뿐, 코드 분기를 사람이 나중에 고르는 구조가 아니다. 둘 다 실패하면(3번 사다리 = 헤드리스 브라우저 리다이렉트 체인 완주) 이 phase 를 중단하고 갭 클로저 플래닝으로 넘긴다.

**1) `src/main/login-mode.ts` (신규, electron 무의존)**

**2) `src/main/services/api-auth-client.ts` (신규)**

모듈 상수: `ACCOUNT_API_BASE = "https://accountapi.weverse.io/web/api"`, `FANS_ME_URL = "https://fanevent-v2.weverse.io/api/fan-api/v1/fans/me"`, `ACCOUNT_TIMEOUT_MS = 10_000`, `TARGET_SERVICE_ID = "weverse"`, `REFRESH_TOKEN_COOKIE_TTL = 0`.

`REFRESH_TOKEN_COOKIE_TTL` 은 PROJECT.md 계약에 필드명만 있고 값은 미검증이다. 0(세션 수명)을 보내고, 서버가 이 필드를 문제 삼아 `-26000` 을 돌려주면 Task 3 체크포인트의 지시대로 `2592000` 으로 한 번 재시도한다. 주석이 아니라 상수 이름과 이 계획서로 근거를 남긴다.

`export class ApiAuthError extends Error` — `weverse-api.ts:33-42` 의 `WeverseApiError` 와 동일한 shape: `constructor(public readonly code: string, message: string, public readonly statusCode?: number)`, `this.name = "ApiAuthError"`. 계정 API 의 code 는 숫자(-25044 등)이므로 문자열로 변환해 보존한다(`"-25044"`). 합성 코드는 `NETWORK_ERROR`, `PARSE_ERROR`, `HTTP_ERROR`, `FANEVENT_TOKEN_UNAVAILABLE` 4종만 쓴다.

exported 인터페이스: `OtpSession { otpSessionId: string; expiresIn?: number }`, `AccountTokens { accessToken: string; refreshToken?: string; serviceUserId?: string; expiresIn?: number }`, `type FaneventTokenSource = "direct" | "exchange"`, `FaneventToken { token: string; source: FaneventTokenSource; fanId: number }`.

`export class ApiAuthClient` — `private readonly fetch: typeof globalThis.fetch;` + `constructor(fetchFn: typeof globalThis.fetch = globalThis.fetch)` (timing-service.ts:20-25 그대로).

private `accountHeaders()`: 매 호출마다 `crypto.randomUUID()` 로 새 `X-ACC-TRACE-ID` 를 만들어 `X-ACC-APP-VERSION: "4.7.1"`, `X-ACC-APP-SECRET: "5419526f1c624b38b10787e5c10b2a7a"`, `X-ACC-SERVICE-ID: "weverse"`, `X-ACC-LANGUAGE: "ko"`, `Content-Type: "application/json"` 과 함께 반환한다. trace ID 재사용은 Pitfall 1 이 지목한 `-26000` 유발 경로다.

private `timedFetch(url, init)`: `weverse-api.ts:21-31` 의 AbortController + setTimeout + finally clearTimeout 형태를 그대로 쓰되, 모듈 전역 fetch 가 아니라 `this.fetch` 를 호출한다. 이것이 두 아날로그를 합치는 유일한 의도적 편차다.

private `postAccount<T>(path, body, extraHeaders?)`: `timedFetch` 호출을 try/catch 로 감싸 `AbortError` 는 `ApiAuthError("NETWORK_ERROR", "네트워크 타임아웃")`, 그 외 예외는 `ApiAuthError("NETWORK_ERROR", "네트워크 에러: ...")` 로 바꾼다(weverse-api.ts:60-67 형태). 응답이 `res.ok` 가 아니면 바디를 JSON 으로 읽어 `code`/`message` 를 뽑아 `new ApiAuthError(String(code), String(message), res.status)` 를 던지고, 바디 파싱이 실패하면 `ApiAuthError("HTTP_ERROR", \`계정 API 실패: HTTP ${res.status}\`, res.status)` 를 던진다. 성공 바디 파싱 실패는 `ApiAuthError("PARSE_ERROR", ...)`.

public 메서드 5개:
- `requestOtpSession(email: string): Promise<OtpSession>` — `POST ${ACCOUNT_API_BASE}/v2/auth/otp-sessions`, 바디 `{ email }`.
- `loginWithCredentials(email, password, otpSessionId): Promise<AccountTokens>` — `POST ${ACCOUNT_API_BASE}/v4/auth/token/by-credentials`, 바디 `{ email, password, otpSessionId }`.
- `verifyOtp(email, password, otpSessionId, otpCode): Promise<AccountTokens>` — `POST ${ACCOUNT_API_BASE}/v3/auth/token/by-credentials-with-otp`, 바디 `{ email, password, otpSessionId, otpCode, refreshTokenCookieTtl: REFRESH_TOKEN_COOKIE_TTL }`.
- `exchangeForService(accountAccessToken: string, targetServiceId = TARGET_SERVICE_ID, departureServiceId = TARGET_SERVICE_ID): Promise<AccountTokens>` — `POST ${ACCOUNT_API_BASE}/v2/auth/token/by-access-token`, 바디 `{ targetServiceId }`, 추가 헤더 `Authorization: \`Bearer ${accountAccessToken}\`` 와 `X-ACC-SERVICE-ID: departureServiceId`(기본 헤더의 값을 덮어쓴다). `departureServiceId` 파라미터가 존재하는 이유는 RESEARCH.md 가정 A1(출발 서비스 ID 가 `weverse` 로 충분한지)이 미검증이기 때문이다 — Task 3 체크포인트에서 다른 후보를 시도해야 할 때 코드 구조를 바꾸지 않고 인자만 넘길 수 있게 미리 열어 둔다.
- `probeFaneventToken(token: string): Promise<number | null>` — `GET FANS_ME_URL`, 헤더 `Authorization: Bearer ...` + `X-FEV-APP-SOURCE: "FAN_EVENT"` + `Accept: "application/json, text/plain, */*"` (weverse-api.ts:13-19 와 동일). 200 이고 바디에 숫자 `fanId` 가 있으면 그 값을, 401 이면 `null` 을, 그 외 상태는 `ApiAuthError("HTTP_ERROR", ..., res.status)` 를 던진다.

사다리 본체 `acquireFaneventToken(accountAccessToken: string): Promise<FaneventToken>`:
- rung 1 — `probeFaneventToken(accountAccessToken)` 이 fanId 를 주면 `{ token: accountAccessToken, source: "direct", fanId }` 를 즉시 반환하고 교환 호출을 아예 하지 않는다. RESEARCH.md Open Question 3(교환 자체가 불필요할 가능성)이 참이면 여기서 끝난다.
- rung 2 — rung 1 이 `null` 이면 `exchangeForService(accountAccessToken)` 로 교환한 뒤 그 `accessToken` 으로 다시 `probeFaneventToken` 을 호출하고, fanId 를 얻으면 `{ token: exchanged.accessToken, source: "exchange", fanId }` 를 반환한다.
- 둘 다 실패하면 `ApiAuthError("FANEVENT_TOKEN_UNAVAILABLE", "팬이벤트 토큰을 확보하지 못했습니다 — 계정 토큰 직접 사용과 by-access-token 교환이 모두 401")` 를 던진다. 이 예외를 절대 삼키지 않는 것이 Pitfall 5 의 핵심이다.
- 각 사다리 진입/결과를 `logService.info("ApiAuthClient", ...)` 로 남기되 토큰은 `maskToken()` 을 통과시킨다.

이 파일은 electron 런타임 모듈을 어떤 형태로도 import 하지 않는다. 세션/쿠키 API 를 건드리면 브라우저 모드의 `persist:weverse` 파티션과 토큰이 뒤섞인다(Pitfall 4). 어떤 메서드에서도 요청 바디 전체를 문자열화해 로그에 넣지 않는다 — 이메일 앞 3글자, otpSessionId, 마스킹된 토큰만 로그에 남긴다(Pitfall 3).
