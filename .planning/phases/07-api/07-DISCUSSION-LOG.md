## 경고 후 흐름 + 토큰 갱신

**논의 중 발견한 결함:** `apply-engine.ts:146` 이 실행 시작 시점의 토큰을 지역 변수로 붙잡고
대기 후 `submitApplication(..., token, ...)` 에 넘긴다 — 대기 중 재로그인해도 새 토큰이 POST 에
반영되지 않는다.

### Q1. 만료 경고가 뜨면 신청 자체를 막을까?

| Option | Description | Selected |
|--------|-------------|----------|
| 막지 않는다 — 경고 + 재로그인 유도만 | 예측 오류로 앱이 이벤트를 놓치게 하는 상황 방지 | ✓ |
| arm 자체를 차단 | 서버가 토큰을 연장해주는 경우에도 사용자를 막음 | |
| arm 허용, POST 직전 최종 게이트 | time-guard/post-guard 계열 가드 추가 | |

**User's choice:** 막지 않는다 — 경고 + 재로그인 유도만

### Q2. 대기 중 재로그인한 새 토큰을 실행 중인 신청에 어떻게 반영할까?

| Option | Description | Selected |
|--------|-------------|----------|
| POST 직전 authService.token 재조회 | 최소 변경. null 이면 기존 UNAUTHORIZED 경로 | ✓ |
| 재로그인 이벤트 구독해 갱신 | 구독 해제 누락·중복 구독 등 새 실패 모드 | |
| 재로그인 시 arm 해제 — 사용자가 다시 arm | 신청 직전이면 다시 arm 할 시간이 없음 | |

**User's choice:** POST 직전 authService.token 재조회

### Q3. 대기 중 재로그인 실패로 기존 토큰까지 잃는 상황은?

| Option | Description | Selected |
|--------|-------------|----------|
| 기존 토큰 백업 후 실패 시 복원 | POST 는 Bearer 헤더만 쓰므로 쿠키가 지워져도 복원이 실효적 | ✓ |
| 그대로 허용 + 경고문에 명시 | 선착순 직전에 사용자에게 도박을 강요 | |
| 대기 중 재로그인 금지 | R022 의 "재로그인 유도"가 사실상 무력화 | |

**User's choice:** 기존 토큰 백업 후 실패 시 복원
**Notes:** `credentialLogin()` 이 시작 시 기존 we2_access_token 쿠키를 먼저 지운다는 점,
그리고 `weverse-api.ts:15` 의 `commonHeaders()` 가 Authorization Bearer 헤더를 쓴다는 점을
확인한 뒤 나온 결정.
