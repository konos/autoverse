Purpose: R019 는 05-01(halted) 에서 로그인이 막혀 도달조차 못 한 상태다. 사다리 로직 자체는 이미 구현·단위

CDP 폴백)와 판정에 필요한 관측성만 만든다. D-04 에 따라 이것은 **스파이크**이며 API 모드 제품 구현이 아니다 —
최소 코드로 유지하고, 기존 브라우저 로그인 동작과 ApplyEngine 소비 경로는 건드리지 않는다.

D-01 에 따라 이 플랜은 무효 전제(3단계 OTP 로그인) 위에 서 있던 구 05-01/05-02 를 대체해 재작성된 것이다.

이 플랜이 구현하는 결정(D-02/D-03/D-04)은 CONTEXT.md 에서 모두 **reversible** 로 기록되어 있다 —
토큰 확보 지점만 바뀌는 국소 변경이고 사다리/클라이언트 셸은 선택과 무관하게 유지되므로, reversibility
게이트(`checkpoint:decision`)를 삽입하지 않는다.

import 하지 않는다 — 순수 입력/출력만 다루는 함수 모음이다. `CookieLike` 인터페이스

`summarizeCookies(cookies)` 는 각 쿠키를 `<name>(domain=<domain>,len=<value.length>,httpOnly=<bool>)` 형태로
콤마 조인한 문자열을 반환한다 — `value` 자체는 어떤 경로로도 결과 문자열에 넣지 않는다.

반환한다 — 토큰의 접두/접미 문자는 반환값에 포함하지 않는다 (`validateToken()` 이 기존에 20자 prefix 를 찍는 것과
달리, 새 캡처 경로는 불투명 토큰일 가능성이 있으므로 값 조각을 아예 노출하지 않는다).

`src/main/services/auth-service.ts` 에 다음을 추가한다. (1) 생성자

기존 필드 초기화(`private apiClient = new ApiAuthClient()`)를 생성자 대입으로 바꾸되 파일 끝의 `new AuthService()`

`verdict: "pass" | "fail" | "skipped"`, `tokenSource: "cookie" | "cdp" | "none"`,
`ladderSource: "direct" | "exchange" | null`, `fanId: number | null`, `reason: string`.
(3) public `async runAccountTokenLadderSpike(trigger: string): Promise<AccountTokenLadderSpikeResult>` 를 추가한다.
동작 순서는 — 단일 비행 플래그 `spikeInFlight` 가 이미 true 면 즉시 `skipped`/`already-running` 반환;
아니면 플래그를 세우고 `try/finally` 로 해제; `session.fromPartition("persist:weverse").cookies.get({})` 로
**필터를 전혀 주지 않고** 전량 열거(D-02 경로 A, Pitfall 1 — 도메인이나 이름으로 좁히면 `account.weverse.io` 에만
스코프된 쿠키를 놓친다); `accountTokenDiscovery: partition=persist:weverse cookies=<개수>` 와
`summarizeCookies()` 결과를 `logService.info("AuthService", ...)` 로 남김; `pickAccountTokenCookie()` 로 후보 선정 후
`accountTokenDiscovery: candidate=<name>@<domain> len=<n>` 또는 `accountTokenDiscovery: candidate=none` 로그;
후보가 없으면 Task 2 가 붙일 CDP 캡처 핸들(`this.accountTokenCapture`)에서 토큰을 읽어 폴백 —
Task 1 시점에는 이 필드가 항상 `null` 이어도 되며 `tokenSource="none"` 으로 떨어지는 경로가 정상 동작하면 된다;
토큰을 확보했으면 `describeTokenShape()` 결과와 `matchesWe2Cookie=<확보한 토큰이 현재 cachedToken 과 문자열 동일한지>`
를 로그로 남기고 `this.apiClient.acquireFaneventToken(token)` 을 호출; 성공 시 verdict `pass` 와 `source`/`fanId` 기록,
`ApiAuthError` 발생 시 verdict `fail` 과 `err.code`/`err.message` 를 `reason` 에 기록(예외를 재던지지 않는다 —
스파이크는 관측이 목적이고 로그인 흐름을 깨뜨리면 안 된다); 마지막에 반드시
`accountTokenLadderSpike: verdict=<v> tokenSource=<s> ladderSource=<l> fanId=<n|none> reason=<r>` 한 줄을 남긴다.
**이 메서드는 `this.cachedToken` 과 `this.cachedFanId` 에 절대 대입하지 않는다** — ApplyEngine 이 읽는
`authService.token` 을 스파이크가 바꾸면 로드맵 Success Criteria 3(무변경 소비)이 무너진다.
(4) `credentialLogin()` 의 `result === "token"` 분기에서 `saveCredentials(...)` 직후·`cleanupHeadless()` 직전에
`void this.runAccountTokenLadderSpike("credentialLogin").catch(...)` 로 **await 하지 않고** 시작한다 —
로그인 응답 지연(사다리는 최대 3회 HTTP, 각 10초 타임아웃)이 기존 로그인 UX 를 바꾸지 않게 하기 위함이다.
