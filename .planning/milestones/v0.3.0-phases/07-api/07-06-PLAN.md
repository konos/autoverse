<design_decision>
## G-01: 두 수정 방향 중 App.tsx 이벤트 재판정(방향 2)을 택한다

07-REVIEW.md CR-01 과 07-VERIFICATION.md `missing:` 1번은 두 방향을 제시했다.

**방향 1 — `AuthService.login()` 이 팝업이 닫히거나 토큰이 추출될 때까지 resolve 하지 않는
Promise 를 반환한다.** 기각한다. 근거:

1. **published contract 변경이다.** `login()` 은 `auth:open-login` IPC 핸들러가 그대로
   전달하는 반환값이고, 호출부가 두 곳(`handleLogin()`, `handleReloginFromWaiting()`)이다.
   두 곳 모두 `finally` 에서 `setLoginLoading(false)` 를 하므로, resolve 를 팝업 수명까지
   미루면 **로그인 창이 열려 있는 내내 로그인 패널 전체가 로딩 상태로 잠긴다.**
2. **영구 pending 실패 모드가 새로 생긴다.** 사용자가 팝업을 닫지도 로그인하지도 않으면
   IPC invoke 가 영원히 pending 이다. 현재 코드에는 `login()` 에 타임아웃이 없다.
3. **되돌리기 비용이 비대칭이다.** 방향 1 은 `one-way` 급 결정(아래 `<reversibility>` 참조)인
   반면 방향 2 는 순수 함수 1개 + 호출 지점 1줄이라 삭제하면 오늘 동작으로 정확히 돌아온다.
4. **회귀 테스트가 실질을 못 잡는다.** 방향 1 의 테스트는 `login()` 의 resolve 타이밍 계약을
   보게 되는데, 그것이 참이어도 "배너가 갱신된다"는 이 진실은 여전히 증명되지 않는다.
   방향 2 는 판정→엔진→뷰 사슬을 그대로 조립해 **경고가 실제로 사라지는 것**을 단언할 수 있다.

**방향 2 — `App.tsx` 의 `onAuthEvent` 가 `apply-execution` 단계에서 인증 결과 이벤트를 받으면
재판정을 부른다.** 채택. 검증자 권고와 일치하고, 이 저장소의 확립된 seam
(`decideAuthEventNavigation()` — "대기 중 어떤 인증 이벤트가 무엇을 유발하는가")에 정확히
얹힌다. `login-success` 는 브라우저 모드(`auth-service.ts` 의 `pollForToken()`)와 API 모드
(`extractTokenFromCookies()`) **양쪽 모두**에서 `cachedToken` 을 채운 **직후**에 emit 되므로,
이 이벤트를 받은 시점의 `authService.token` 은 이미 새 토큰이다 — 재판정이 유의미하다.

## G-02: 기존 `finally` 블록의 재판정 호출은 남기되 주석의 거짓말을 고친다

`handleReloginFromWaiting()` 의 `finally` 재판정은 API 모드의 실패 분기(`none`/`corrupted`/
`unavailable`)처럼 **인증 이벤트가 아예 발생하지 않는 경로**에서는 유일한 재판정 트리거다.
삭제하지 않는다. 다만 지금 그 자리의 주석은 "재로그인 시도가 끝나면"이라고 단언하는데 이는
브라우저 모드에서 거짓이므로, 주석을 사실대로 고친다(팝업이 열린 직후의 즉시 재확인이며,
완료 후 재판정은 `onAuthEvent` 경로가 담당한다).

## G-03: `reloginLoading` 은 새 state 를 만들지 않고 기존 `loginLoading` 을 내려보낸다

`handleReloginFromWaiting()` 이 이미 `loginLoading` 을 set/clear 한다. 별도 state 를 추가하면
같은 사실의 출처가 둘이 되어 어긋날 수 있다. `ApplyExecution` 에 `reloginLoading: boolean`
prop 을 새로 추가하고 `App.tsx` 가 `loginLoading` 을 그대로 넘긴다 — 07-REVIEW.md WR-01 의
Fix 가 제시한 두 선택지 중 상태를 늘리지 않는 쪽이다.
</design_decision>
